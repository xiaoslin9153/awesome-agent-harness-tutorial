# Goal 执行串行化

## 目标

在服务商返回 HTTP 429 后，把 Goal Agent 的执行计划改为严格串行，避免再次触发速率限制。

## 决策

1. 任一时刻只允许一个 Subagent 存在。
2. 主 Agent 自己完成章节草稿；Draft 不再拆给并发子 Agent。
3. 章节顺序、Polish、提交、部署检查和进度更新全部串行执行。
4. 一节完成并推送后，才开始下一节。
5. 遇到 HTTP 429 时停止派生新任务，保存会话检查点后按指数退避恢复：60 秒、120 秒、300 秒，上限 900 秒。
6. 恢复后从同一小节的未完成阶段继续，不重启已完成章节。

## 变更

- 更新 `tutorial/writing-pipeline.md` 的 Agent 协作模式。
- 在全面复审与教材发布会话中记录限流原因和新执行方式。
- 总进度表新增 G24 记录该执行策略。

## 作废说明：2026-09-01

本决策已作废，不再作为现行规范。清理记录见 `2026-09-01-clean-legacy-agent-restrictions.md`，进度表 G29。

作废理由：第 1 至 4 条把速率限制这个外部约束固化成了流水线结构，代价是牺牲所有并行度。限流应当靠调用层的重试与退避吸收，而不是通过禁止并发子任务来回避。

唯一仍有参考价值的结论是第 5、6 条的恢复原则——遇到限流时保存检查点、指数退避、从中断的小节继续而不重启已完成章节。这两条属于故障恢复经验，不依赖并行度，遇到限流时仍可参照，但不作为默认执行方式。
