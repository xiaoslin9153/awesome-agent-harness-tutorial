# Tutorial Tech Writing

## 适用范围

用于 `tutorial/<locale>/` 下公开教材的 Draft、Polish 和 Implementation Review。内部治理文档不适用。

## 写作目标

1. 内容翔实：关键机制必须讲透动机、流程、边界、失败和恢复，不能只留结论摘要。
2. 深入浅出：先建立直觉，再给出精确机制和失败边界；通俗是表达手段，不是删减理由。
3. 有经验程序员能快速找到源码入口、数据结构、调用链和工程取舍。
4. 每句话都承载信息；删除装饰、重复和空泛过渡，但不删解释性细节。
5. 每章承接上一章问题，并把新产生的矛盾交给下一章。

## 中文与排版

1. 中西文和数字之间加一个半角空格：`3 个 Agent`。
2. 中文语境使用直角引号「」；代码、命令、路径、标识符用反引号。
3. 避免网络流行语、夸张形容词和无定义黑话。
4. 标题只声明主题，不用悬念式标题。
5. 列表项保持平行结构；同一列表不要混写句子和短语。

## 简化表达

1. 一句只表达一个意思；复杂因果拆成多句推进，不省略中间环节。
2. 条件放在动作前面：如果工具被拒绝，先记录审批事件，再返回控制权给模型。
3. 用主动语态点名执行者：Harness 组装上下文，模型选择工具。
4. 用具体动词替换弱化表达：把「处理错误」写成「重试请求或返回失败原因」。
5. 一个段落只讲一个主题；段落长度服从解释需要，不为字数切断因果。
6. 抽象概念必须紧跟例子、图、表格或代码锚点。
7. 不用一个工程隐喻解释另一个工程概念；类比必须贴近日常经验并说明失效边界。

## 结构化改写

1. 先回答读者问题，再展开机制。
2. 开头承接上一章遗留问题；结尾留下下一章问题。
3. 每个机制至少写出一个核心不变量和一条完整因果链。
4. 理论结论和实现证据分开；理想模型不得伪装成框架行为。
5. 流程、状态、交互和数据关系优先使用 Mermaid 图。
6. 复杂对照用表格，避免长段落堆叠多个对象。
7. 初学者主线保持好读，但不设行数限制；不要为了短而删除失败分支、源码证据和设计取舍。
8. 反例不是附录；至少写出 3 个故障模式，并解释错误做法如何破坏不变量。

## 详实展开法

对每个核心机制按九层检查，缺失层必须在 Draft 或 Review 中补齐：

1. **问题**：它解决什么矛盾？没有它会发生什么？
2. **直觉**：用一个准确类比或最小例子建立第一层理解。
3. **定义**：区分理想概念、框架专有类型和口语误用。
4. **正常路径**：数据从哪里来，经过哪些转换，写入哪个状态，最终如何呈现。
5. **参数与环境**：列出关键输入形态、配置组合、宿主差异和版本前提。
6. **失败路径**：超时、取消、畸形输入、权限拒绝、部分副作用分别怎么处理。
7. **常见误解**：解释错误做法为什么会看起来有效。
8. **真实实现**：绑定 commit 和 `path:line`，展示调用链、关键字段和控制流。
9. **取舍**：收益是什么，代价是什么，替代方案是什么，成立条件是什么。

九层不必各占一节；可以融入段落，但不能静默消失。「翔实」不是堆功能清单，而是让读者能够复现推理过程。

## 深入浅出三层法

每个抽象概念按固定顺序解释：

1. **一句话直觉**：让初学者知道为什么要关心它。
2. **精确机制**：用字段、状态、调用顺序或协议替换比喻。
3. **边界与反例**：说明类比在哪里失效，错误实现会破坏什么。

禁止停留在第一层当结论，也禁止跳过第一层直接罗列类型定义。

## 出版级 Review

按顺序检查：

1. **读者**：目标读者能否在 30 秒内说出本节解决什么问题？
2. **主线**：标题、导语、图和正文是否讲同一个问题？
3. **密度**：有没有连续三句表达同一个意思？有没有可删的空话？
4. **完整性**：动机、正常流程、边界、失败路径、恢复和取舍是否齐全？有没有被过度压缩？
5. **易懂性**：抽象概念是否有直觉、精确机制和失效边界三层解释？
6. **术语**：术语首次出现是否给英文原文？后续是否统一？
7. **递进**：开头是否解决上一章问题？结尾是否产生下一章问题？
8. **证据**：框架行为是否有源码路径、commit 或实验结果？
9. **深度**：有没有核心不变量、完整因果链、反例、状态变化和失败分支？
10. **图**：图是否比文字更清楚？节点数量是否可控？
11. **格式**：Front Matter、链接、代码块、表格和 Mermaid 是否有效？
12. **发布**：Polish 和 Implementation Review 都通过后才能标记发布。

## 输出约定

- 小改动直接给出修改后的 Markdown 和一句审稿摘要。
- 大章节输出：主要问题、修改策略、修改清单和遗留风险。
- 不新增事实；需要补充事实时先交给 Draft 或 Implementation Review。
- 如果发现因旧规则被删掉的实质内容，标记 `needs-changes` 并列回待补清单，不得静默接受。
