# Tutorial Tech Writing

## 适用范围

用于 `tutorial/<locale>/` 下公开教材的 Draft、Polish 和 Implementation Review。内部治理文档不适用。

## 写作目标

1. 初学者能顺着主线读懂，不需要额外上下文。
2. 有经验程序员能快速找到源码入口、数据结构和工程取舍。
3. 每句话都承载信息；删除装饰、重复和空泛过渡。
4. 每章承接上一章问题，并把新产生的矛盾交给下一章。

## 中文与排版

1. 中西文和数字之间加一个半角空格：`3 个 Agent`。
2. 中文语境使用直角引号「」；代码、命令、路径、标识符用反引号。
3. 避免网络流行语、夸张形容词和无定义黑话。
4. 标题只声明主题，不用悬念式标题。
5. 列表项保持平行结构；同一列表不要混写句子和短语。

## 简化表达

1. 一句只表达一个意思；超过 30 个汉字且包含逗号时优先拆句。
2. 条件放在动作前面：如果工具被拒绝，先记录审批事件，再返回控制权给模型。
3. 用主动语态点名执行者：Harness 组装上下文，模型选择工具。
4. 用具体动词替换弱化表达：把「处理错误」写成「重试请求或返回失败原因」。
5. 一个段落只讲一个主题；初学者路线段落不超过 6 句。
6. 抽象概念必须紧跟例子、图、表格或代码锚点。
7. 不用一个工程隐喻解释另一个工程概念；类比必须贴近日常经验并说明失效边界。

## 结构化改写

1. 先回答读者问题，再展开机制。
2. 开头承接上一章遗留问题；结尾留下下一章问题。
3. 每个机制至少写出一个核心不变量和一条完整因果链。
4. 理论结论和实现证据分开；理想模型不得伪装成框架行为。
5. 流程、状态、交互和数据关系优先使用 Mermaid 图。
6. 复杂对照用表格，避免长段落堆叠多个对象。
7. 初学者主线保持简洁，但不设行数限制；不要为了短而删除失败分支、源码证据和设计取舍。
8. 反例不是附录；至少写出 3 个故障模式，并解释错误做法如何破坏不变量。

## 出版级 Review

按顺序检查：

1. **读者**：目标读者能否在 30 秒内说出本节解决什么问题？
2. **主线**：标题、导语、图和正文是否讲同一个问题？
3. **密度**：有没有连续三句表达同一个意思？有没有可删的空话？
4. **术语**：术语首次出现是否给英文原文？后续是否统一？
5. **递进**：开头是否解决上一章问题？结尾是否产生下一章问题？
6. **证据**：框架行为是否有源码路径、commit 或实验结果？
7. **深度**：有没有核心不变量、完整因果链、反例、状态变化和失败分支？
8. **图**：图是否比文字更清楚？节点数量是否可控？
9. **格式**：Front Matter、链接、代码块、表格和 Mermaid 是否有效？
10. **发布**：Polish 和 Implementation Review 都通过后才能标记发布。

## 输出约定

- 小改动直接给出修改后的 Markdown 和一句审稿摘要。
- 大章节输出：主要问题、修改策略、修改清单和遗留风险。
- 不新增事实；需要补充事实时先交给 Draft 或 Implementation Review。
