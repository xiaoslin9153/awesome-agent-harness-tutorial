## 背景与问题

当前章节已经覆盖较多机制，但读者反馈存在三个结构性问题：

1. 讲解过于简单，经常停在「框架支持 X」，没有解释状态如何变化、失败走哪条分支、为什么需要该设计。
2. 缺少原理、因果链、反例和工程取舍，难以支撑有经验程序员的系统设计需求。
3. 小节之间更像并列词条，缺少上一章遗留问题和下一章驱动问题的递进关系。

2026-08-23 的量化检查显示：

| 范围 | 证据 |
| --- | --- |
| 16 篇机制章节行数为 112-122 行 | `wc -l` 输出，见会话记录。 |
| 框架基础页行数约为 124-173 行 | 同上。 |
| 多数框架页只有少量源码锚点，9 个页面中 5 个没有可定位锚点 | `rg` 统计 `path:`、`.go`、`.ts`、`.tsx`。 |
| 9 个框架页面中 8 个没有语言代码片段 | `rg -c '^```(ts|typescript|javascript|go|bash)'`。 |

根因不是单篇文笔，而是写作基础设施缺少深度与递进门禁：

1. Skill 过度强调压缩表达，初学者路线不超过 80 行被误解为整章不超过 80 行量级的密度。
2. Draft / Polish 先行，Implementation Review 批量延后，导致框架行为常停留在线索而不是已验证结论。
3. TOC 只记录依赖 ID，没有记录每章要继承的问题、要建立的不变量和要交给下一章的问题。
4. 没有强制反例数量、源码证据密度、代码片段和递进衔接检查。
5. Goal 目标奖励章节数量推进，容易把「完成」理解成「覆盖结构完整」。
6. 框架专题目前只有 overview、Run lifecycle 和 tools 三类粗粒度页，无法承接 C01-C25 的源码级拆解。

## 目标

建立「章节学习契约 + 源码级框架深拆标准」，让每个机制章形成递进课程，让每个框架 × 主题簇提供可验证的实现分析。

## Chapter Depth Contract

每个机制章在进入 Polish 前必须回答：

1. 上一章留下了什么问题？
2. 本章为什么现在出现？
3. 本章保护哪个核心不变量？
4. 正常路径是什么？
5. 失败时哪些状态会损坏？
6. 为什么常见做法会出错？
7. 三家框架如何解决同一矛盾？
8. 本章留给下一章什么问题？

## 推荐章节模板

```text
## 上一章遗留问题
## 本章解决什么矛盾
## 核心不变量
## 理想模型
## 初学者主线
## 机制深拆
## 反例与故障模式
## 设计取舍
## 框架实现对照
## 实现精妙之处
## 自检与面试追问
## 交给下一章的问题
```

约束：

1. 「初学者主线」仍应保持简洁，目标是不啰嗦地讲清原理。
2. 「机制深拆」「框架实现对照」不受初学者主线长度约束。
3. 理想模型必须与真实实现分开；不得把理论写成某家框架的事实。
4. 图优先表达流程、状态、交互和数据关系；不需要图时不强行加图。

## 框架 × 机制矩阵

采用双层结构，避免机制章重复塞入全部源码细节：

1. 机制章负责不变量、通用模型、横向摘要、故障模式和指向框架专题的链接。
2. 框架专题页负责该框架在该机制上的模块地图、核心类型、调用链、源码证据、关键片段和失败分支。

建议按 C01-C25 组成主题簇：

| 主题簇 | 覆盖维度 |
| --- | --- |
| 定位与架构 | C01-C03 |
| Run 生命周期 | C04-C06 |
| Context 与压缩 | C06-C07 |
| Tool Schema 与执行 | C08-C10 |
| 事件与流式 | C11-C12 |
| 审批、沙箱与安全 | C13-C14 |
| 并发与多 Agent | C15-C16 |
| 持久化、恢复与取消 | C17-C19 |
| 可观测性与重放 | C20 |
| 扩展、测试、成本与部署 | C21-C25 |

重叠维度只能有一个主归属；另一个主题簇通过链接引用，避免重复维护结论。

## 框架深拆模板

每个「框架 × 主题簇」至少包含：

1. **原理**：该机制保护的不变量和解决的核心矛盾。
2. **模块地图**：组件职责和数据流，必要时用 flowchart 或 class diagram。
3. **核心类型**：关键字段、所有权、生命周期和边界条件。
4. **调用链**：从入口到模型、工具、持久化、事件或审批的完整路径。
5. **UML**：交互用 sequence diagram，状态迁移用 state diagram，稳定数据关系用 class diagram。
6. **源码证据**：固定 commit、符号名和尽量精确的 `path:line`。
7. **关键片段**：30-50 行内的注释化代码或等价伪代码。
8. **失败分支**：超时、取消、畸形输入、崩溃、权限拒绝和部分副作用。
9. **精妙之处**：设计好在哪，成立前提是什么。
10. **代价与反例**：什么时候变差，错误使用会发生什么。
11. **可迁移模式**：读者自己实现 Harness 时应借鉴什么。
12. **待审清单**：逐条标记 `已验证`、`推断` 或 `未验证`。

## 质量门禁

一章进入 Polish 前必须满足：

1. 至少 3 个明确反例或故障模式。
2. 至少 1 条完整因果链，不能只是功能列表。
3. 至少 1 张能减少文字负担的图或表格。
4. 框架声明绑定固定 commit 和尽量精确的 `path:line`。
5. 关键框架行为至少有一个代码片段或伪代码。
6. 开头承接上一章问题，结尾留下下一章问题。
7. 不允许只写「它支持 X」；必须说明状态如何变化、谁拥有状态、失败走哪条分支。
8. Polish 与 Implementation Review 分开验收；批量草稿阶段可以延后 Implementation Review，但必须在 Front Matter 记录待核对清单。

## 外部写作参照

以下来源用于对照成熟技术书的组织方式，不作为框架事实来源：

1. [Designing Data-Intensive Applications](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/)：先建立不变量，再展开真实系统的工程取舍。
2. [Google Technical Writing Courses](https://developers.google.com/tech-writing)：句子清晰、主动语态、结构先行。
3. [The Learning Scientists: Six Effective Learning Strategies](https://www.learningscientists.org/blog/2016/6/23-1)：检索练习、交错练习和具体例子帮助长期记忆。
4. [C4 Model](https://c4model.com/)：按 Context、Container、Component、Code 分层描述架构。
5. [Anthropic: Claude Code Best Practices](https://www.anthropic.com/engineering/claude-code-best-practices)：真实 Agent 使用模式与工作流。
6. [Simon Willison: Claude Code anatomy](https://simonwillison.net/2025/Sep/8/claude-code-anatomy/)：把产品行为还原成工具循环和上下文机制。
